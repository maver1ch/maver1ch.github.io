## Problem

HTI Group needed one chatbot that could both answer from scattered HR knowledge and act for employees — and then survive the jump from quick demo to enterprise production.

- **Fragmented knowledge** spread across PDF, Word and Excel files, where headers, paragraphs and tables carry different meaning.
- **Off-the-shelf RAG broke down** on complex policy queries that crossed multiple sub-domains: leave, payroll, benefits, tooling.
- **Answers were not enough**: staff also wanted the bot to do things — book a meeting room, calculate income tax, open an IT ticket — and only when they had the right permission.
- **POC-to-production was non-negotiable**: the agent layer had to move to AWS without a rewrite.

<PhaseMarker label="Phase 1 — Proof of Concept" />

<ArchitectureSection
  step="01"
  title="High-Level System Architecture"
  image="/assets/case-studies/hti/01-high-level-architecture.png"
  alt="High-Level System Architecture"
>
Every request enters through a **FastAPI gateway**, picks up its **session memory**, and reaches a **router agent** that hands it to one of three specialists — **Knowledge**, **Action** or **ChitChat** — each running its own **ReAct loop** of reasoning and tool calls. In the POC the Knowledge agent's tools sit on **Qdrant** (vectors), **MongoDB** (full-text and metadata), **Neo4j** (knowledge graph) and the HR files themselves (tabular data). Whichever agent answers, the user gets one unified response.
</ArchitectureSection>

<ArchitectureSection
  step="02"
  title="Multi-Agent Router (ReAct)"
  image="/assets/case-studies/hti/02-multi-agent-router.png"
  alt="Multi-Agent Router"
>
The brain of the chatbot. The **Knowledge agent** decides which sources to query, calls **vector, full-text, graph and tabular tools in parallel**, and checks whether the context is sufficient — if not, it loops back and searches again before writing the final answer. The **Action agent** first checks that all parameters are present (and asks the user for any that are missing), then runs an **RBAC check** before calling external APIs: summarize a **Discord** thread, book or check a **meeting room**, calculate **income tax**, or open an **IT support ticket**. A denied check returns an authorization error, never a silent action. The **ChitChat agent** handles general conversation with a web search tool. Splitting the work this way makes each agent independently testable.
</ArchitectureSection>

<ArchitectureSection
  step="03"
  title="Data Ingestion Pipeline"
  image="/assets/case-studies/hti/03-data-ingestion-pipeline.png"
  alt="Data Ingestion Pipeline"
>
An offline pipeline in four stages. **Docling** parses the layout of PDF, Word and Excel files into headers, paragraphs and tables. A semantic merger builds **parent chunks** for context, which a recursive splitter cuts into small **leaf chunks** for search — **hierarchical semantic chunking**. An **LLM context injector** then rewrites each leaf chunk with the context of its parent, so every retrieval unit still makes sense on its own, while an **LLM graph extractor** turns parent chunks into subject–predicate–object **triplets** for Neo4j. Finally, leaf chunks are embedded with **BGE-M3** into Qdrant, and content plus metadata go to MongoDB for full-text search.
</ArchitectureSection>

<PhaseMarker label="Phase 2 — Enterprise Production" highlight />

<ArchitectureSection
  step="04"
  title="AWS Cloud Migration"
  image="/assets/case-studies/hti/04-aws-migration-architecture.png"
  alt="AWS Cloud Migration Architecture"
  highlight
  challenge="The POC ran on a single box with local databases. Production needed private networking, managed data stores, and a clean split between long-running agent work and short tool calls — without rewriting the agent layer."
>
Clients call **API Gateway** (OAuth2 / JWT validation) over SSE REST; traffic goes through an ALB into **ECS Fargate**, where a **Chat Service** (FastAPI gateway) and an **Agent Service** (LangGraph multi-agent) talk over **gRPC streaming**. Short, async tool invocations run on **AWS Lambda**. Inference goes to **Amazon Bedrock (Claude Sonnet)** through an interface **VPC endpoint**, and S3 through a gateway endpoint, so nothing leaves the private network. The POC stores map to managed services — OpenSearch for vectors, Neptune for the knowledge graph, DocumentDB for metadata — plus RDS PostgreSQL for relational data and ElastiCache for sessions and caching.
</ArchitectureSection>

<ArchitectureSection
  step="05"
  title="Serverless Ingestion Pipeline"
  image="/assets/case-studies/hti/05-serverless-ingestion-pipeline.png"
  alt="Serverless Ingestion Pipeline"
  highlight
>
On AWS, ingestion is **event-driven and serverless**. An admin uploads a document to **S3**; the **S3 event notification** triggers a **Lambda ingestion engine** in a private subnet. It generates embeddings with a **Bedrock** embedding model through a VPC endpoint, then indexes vectors in **OpenSearch**, loads triplets into **Neptune**, and saves content and metadata to **DocumentDB**. No compute sits idle between uploads, and bursts of new documents scale out on their own.
</ArchitectureSection>

## Outcome

- **One chatbot that answers and acts** — HR knowledge from PDF, Word and Excel behind a single interface, plus RBAC-checked actions on Discord, meeting rooms, income tax and IT tickets.
- **POC to AWS production without rewriting the agents** — the same LangGraph agents now run on ECS Fargate and Lambda, with local stores swapped for managed AWS services.
- **Private by design** — Bedrock and S3 reached only through VPC endpoints; OAuth2 / JWT checked at the API Gateway.
- **Repeatable delivery** with CI/CD via AWS CDK.
- **Reusable agent and infra patterns** that informed downstream projects at FPT Software.
