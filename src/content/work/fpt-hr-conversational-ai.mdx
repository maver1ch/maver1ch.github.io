## Problem

Covestro AG's HR assistant was live across countries, but had spent almost a year in maintenance-only mode with nothing measured.

- **Improvements ran on guesswork** — no numbers behind any of them: **cost metrics** never emitted, **dashboards** dead for a year, the **evaluation pipeline** broken.
- **No production-like test environment** — DEV ran on a year-old **QA knowledge base**, so passing on DEV proved nothing about PROD.
- **Dangerous deploy path** — merging to `main` shipped straight to production, with no **unit tests**, no **`cdk diff`** and a **guardrail** stuck on a draft version.
- **Monolith mixing reasoning with execution** — six **hard-coded agents** sharing one Lambda with retrieval, permissions and ServiceNow / Workday calls; every prompt change meant a **redeploy**.
- **No single point of enforcement** — the **permission filter** was monkey-patched into the retriever, and HR-only content could not be published safely.

<ArchitectureSection
  step="01"
  title="Take-over Audit: Measure Before Touching Code"
  image="/assets/case-studies/covestro/images/01-takeover-audit.png"
  alt="The inherited Tailor v1 architecture with measured findings pinned to the knowledge base, the LLM, the guardrail, CloudWatch and CI/CD"
>
I worked in three phases: read the system offline, then use the one window of cloud access to **measure, not fix**, then turn the numbers into a **12-item backlog** with evidence on every line. Two scores set the direction — **recall@5 52.7%** for retrieval, **faithfulness 74.5%** for generation — so the lever was what the model sees, not the model itself. Token metrics were defined but **never emitted**, and three of four dashboards were dead.
</ArchitectureSection>

<ArchitectureSection
  step="02"
  title="LLM Observability: Tracing, Cost & Quality"
  image="/assets/case-studies/covestro/images/02-llm-observability.png"
  alt="One chat turn traced step by step in Langfuse, with personal data masked at the source; traces power token usage, cost tracking, per-step latency, debugging, a golden-dataset baseline and prompt versioning"
  highlight
  challenge="Cost metrics were never emitted and CloudWatch showed nothing inside an answer, so nobody could say why an answer was wrong, how long each step took, or what a model change would cost."
>
Observability came first, because every later fix needed a way to measure its effect. I integrated **Langfuse** so every turn became one trace — each LLM call, retrieval and tool call as a span, with **token usage, cost and latency per step**. Model **cost comparison** became a query, not a guess; a bad answer became a trace to **debug** step by step; every change had a **golden dataset** of ~200 HR questions as its baseline, with **prompts versioned** alongside. Because HR questions carry **personal data**, it was masked before leaving the app, and production kept **metadata only**.
</ArchitectureSection>

<ArchitectureSection
  step="03"
  title="Ingestion Pipeline: Chunking & Table Fidelity"
  image="/assets/case-studies/covestro/images/03-knowledge-ingestion.png"
  alt="Hourly ServiceNow ingestion pipeline on AWS: EventBridge, Lambda, SQS with DLQ, DynamoDB, an attachment conversion branch, S3, a chunking Lambda, Bedrock Knowledge Base and OpenSearch"
>
A full corpus scan — every article checked against the source, not a sample — found two faults in the same layer. The HTML→Markdown converter flattened tables to one cell per line, so salary and benefit grids lost the rows and columns that gave the numbers meaning. And chunking was **fixed-size**, cutting straight through those tables. I rebuilt the converter so **real Markdown tables survive**, then moved ingestion to **hierarchical chunking** — parent chunks for context, child chunks for precision — with **table-aware boundaries**: a split landing inside a table extends to take the whole table instead of severing it.
</ArchitectureSection>

<ArchitectureSection
  step="04"
  title="Production-like DEV: Mirroring the Production Knowledge Base"
  image="/assets/case-studies/covestro/images/04-kb-mirror.png"
  alt="Cross-account mirror of the production knowledge base into DEV, with a runtime SSM switch between the mirror and the stale QA knowledge base"
  challenge="DEV read a separate QA knowledge base — 815 articles against 995 in production, some one to two years old. Passing on DEV proved nothing about production."
>
I built a **second knowledge base in DEV that mirrors production**. A DEV role reads the production bucket with **`GetObject` and `ListBucket` only**, and a mirror Lambda syncs **by ETag**, so re-runs simply reconcile. It uses the same **embedding and chunking** as production, and the live knowledge base is an **SSM parameter read at runtime**. This made the move to **Bedrock Claude Sonnet 4.5** provable before it shipped.
</ArchitectureSection>

<ArchitectureSection
  step="05"
  title="Semantic Caching Layer"
  image="/assets/case-studies/covestro/images/05-semantic-cache.png"
  alt="Semantic cache on ElastiCache: questions embedded with Cohere Multilingual v3, cosine match scoped by permission, hits served directly, misses run the RAG path and write back"
  highlight
  challenge="HR questions repeat constantly in a hundred wordings, so a key cache never hits — and with per-country visibility, a shared cache could leak."
>
About **85% of questions hit the same articles**. Questions are embedded with **Cohere Multilingual v3** and matched in **ElastiCache** by cosine; at **0.95 or above** the stored answer is served, skipping retrieval and the LLM. Misses run normal RAG and write back with a **24h TTL**. PII is masked first, and the **cache key carries the user's permission scope**. Repeats return in **~150 ms** with zero tokens.
</ArchitectureSection>

<ArchitectureSection
  step="06"
  title="HR4HR: Restricted Knowledge Base, No Leakage Window"
  image="/assets/case-studies/covestro/images/06-hr4hr-permissions.png"
  alt="HR4HR: every document labelled at import, a server-side HR check each turn, one filter at a single choke point, and two switches with a five-step rollout that turns the filter on before the HR content"
  highlight
  challenge="134 internal HR articles had to share one index with ~1,000 public ones — visible to HR only, with no leakage window even mid-rollout."
>
Each document carries an `access_level` tag. `is_hr` is computed **server-side on every turn**, cached briefly and **fail-closed**; client flags are never trusted. The filter sits at a **single choke point** every agent inherits. The rollout followed one invariant — filter **on before** the first restricted document lands — across **four gated stages**. Non-HR users saw **0 restricted references**.
</ArchitectureSection>

<PhaseMarker label="Phase 2 — Tailor 2.0: platform migration" highlight />

<ArchitectureSection
  step="07"
  title="Tailor 2.0 Platform: Engine + MCP Services"
  image="/assets/case-studies/covestro/images/07-tailor-2-platform.png"
  alt="Tailor 2.0 on AWS: a stateless agent engine on Lambda with agent config in DynamoDB, three MCP services invoked as Lambdas, a tool-audit table and the tailor-core data plane"
>
**Prompts and tools are data, not code** — that is the biggest difference between v1 and 2.0. A **stateless engine** — LangGraph ReAct behind a streaming Function URL, history arriving with every request — owns the conversation loop, guardrails on input and output, and identity; it never calls a business API. Three **MCP services** for knowledge, ServiceNow and Workday expose typed tools through the MCP SDK and are invoked as Lambdas with a JSON-RPC payload; each resolves permissions server-side and writes an audit row. Agents live in **DynamoDB** — one active revision, a tool allowlist resolved through a **three-layer registry** — so a new source is a new service plus one config item.
</ArchitectureSection>

<ArchitectureSection
  step="08"
  title="Release Gates: Quality Parity & Latency"
  image="/assets/case-studies/covestro/images/08-release-gates.png"
  alt="Two release gates: a hand-scored 30-question parity run, then a latency waterfall from 18.6 s to 6.3 s against the legacy 7.7 s"
>
Quality and speed were gated separately. **Parity first**: 90 reference questions covering every case type and the edge cases, only the switch flipped, scored by an **LLM judge** whose scores the HR team then reviewed — the new platform matched or beat the old one on **90 of 90**. For latency, joining client timings with engine logs on `conversation_id` exposed **fake streaming**: nothing was sent until the whole answer was ready. Three fixes took **time to first token (P50) from 18.6 s to 6.3 s**, below the legacy 7.7 s.
</ArchitectureSection>

<ArchitectureSection
  step="09"
  title="Zero-Downtime Cutover Behind an SSM Switch"
  image="/assets/case-studies/covestro/images/09-cutover-ssm-switch.png"
  alt="An SSM switch inside the v1 chat Lambda sends each request either to the IAM-signed agent engine or to the old monolith agents, with no per-request fallback"
  highlight
  challenge="Users arrive through a third-party chat platform that could not be changed, with no downtime budget — every step had to be reversible in under a minute."
>
Every request already passed through the monolith's chat Lambda, so the switch went there: one **SSM parameter**, read per request. When it is on, the Lambda **signs the same request with IAM**, forwards it to the engine and streams the answer back; when it is off, the old agents answer as before. There is deliberately **no automatic per-request fallback** — it would run a turn twice, possibly creating a duplicate ticket, and hide failures from alarms. Switching is a person's decision: **one value, no deploy**, with rollback **rehearsed at 34.8 s**.
</ArchitectureSection>

<ArchitectureSection
  step="10"
  title="Data-Plane Ownership Transfer, Zero ID Changes"
  image="/assets/case-studies/covestro/images/10-data-plane-migration.png"
  alt="Knowledge base, OpenSearch collection, tables, buckets and the ingestion pipeline moved from the monolith CDK app to a new data repo by stack refactor and cdk import"
  highlight
  challenge="The knowledge base, OpenSearch collection, tables and ingestion pipeline still belonged to the monolith. Rebuilding meant re-ingesting every article and new ids everywhere."
>
A spike settled it: **move, don't rebuild**. Stateful resources got `Retain`, consumers read ids from config, and every window had abort criteria. When the first window was **aborted**, **16 probe refactors** isolated an undocumented CloudFormation rule, and a "touch" step became standard. The next window moved **11 resources in 45 seconds** — **zero id changes, no re-ingestion**.
</ArchitectureSection>

<PhaseMarker label="Across both phases — delivery pipeline" />

<ArchitectureSection
  step="11"
  title="Delivery Pipeline: CI/CD, IaC & LLM Regression"
  image="/assets/case-studies/covestro/images/11-delivery-pipeline.png"
  alt="Before: merging to main deployed straight to production with no tests or infra diff. After: pull-request CI with coverage, a cdk diff gate, DEV deploy through OIDC with smoke tests, an LLM regression suite, and a manual production dispatch"
>
At takeover, merging to `main` was the production deploy, with no unit tests and no infrastructure diff. Now every repo runs one pipeline: lint, unit tests with an **80% coverage floor** and a **`cdk diff` against production** on each pull request; merging deploys to DEV through **GitHub OIDC** with an automatic smoke test. Any prompt, model or retrieval change must pass an **LLM regression suite** against the last release before a **manual production dispatch**. Features ship switched off, so **deploy is not release**.
</ArchitectureSection>

- **From guesswork to measurement** — a production assistant nobody could observe became one with a baseline, tracing, and a backlog chosen by numbers; **19 production releases** as sole developer.
- **Repeat questions in ~150 ms** from a semantic cache that stays inside the user's permission scope.
- **HR-only knowledge base with zero leakage** — fail-closed filter at a single choke point, rolled out in an order that never opened a window.
- **Zero-downtime migration** to a multi-service agent platform — parity 90/90 and latency 18.6 → 6.3 s proven first, cutover behind an SSM switch with a rehearsed rollback.
- **Stateful data plane moved between CDK apps with zero id changes** and no re-ingestion, plus an undocumented CloudFormation constraint turned into a reusable procedure.
